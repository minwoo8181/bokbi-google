## 1. 복비(Bokbi) 시스템의 정의와 존재 이유

### 1.1 서비스 본질 및 해결하려는 문제
- **전통 부동산 거래의 고질적 병폐**:
  - 부동산 계약 체결 당일, 계약서에 도장을 찍기 직전까지 집주인과 중개사는 서로 눈치를 보며 "복비를 얼마나 깎아줄 수 있는지 / 다 받아야 하는지" 감정 소모적 흥정을 벌입니다.
  - 집주인은 "더 깎고 싶지만 중개 서비스 질이 떨어지거나 매물을 안 보여줄까 봐" 불안해하고, 중개사는 "손님이 떠날까 봐" 불안해합니다.
- **복비(Bokbi)의 솔루션**:
  - "계약 당일 현장에서 어색하게 흥정하지 말고, **국토부 실거래가와 시장 수급 데이터를 기반으로 중개사도 납득할 수준의 복비를 먼저 제안하고, 광고 없이 진성 매물을 연결하는 상생 플랫폼**을 만들자."
- **플랫폼이 제공하는 상생 가치 (Win-Win)**:
  - **집주인**: 실거래·매물 데이터로 계산한 합리적인 중개보수를 미리 제안하고 합의된 보수로 계약하며, 매칭 전까지 상세 동·호수와 전화번호가 비공개 보호됨.
  - **공인중개사 (GTM: 매물이 있는 단지 내 부동산을 제외한 모든 중개사)**: 광고비 없이 매도 의사가 확실한 진성 매물을 확보. 지역 친목회의 비회원 공동중개 배제 같은 카르텔을 우회하는 통로(MEMORY.md §2 조사).

### 1.2 핵심 비즈니스 룰 및 블라인드 안심 보호 원칙
1. **100% 블라인드 보호 ➔ 매칭 성사 후 안전 언마스킹 (Unmasking)**:
   - **매칭 전**: 중개사 화면에는 `[다산자이] 34평 10*동 ***호 · 중층` 및 `010-*8**-**3*`으로 마스킹되어 개인정보 유출 원천 차단.
   - **매칭 수락 & 집주인 확정 시**: 집주인이 선택한 특정 중개사에게만 동·호수 전체(`104동 1802호`)와 실연락처가 잠금 해제되어 네이버 부동산 확인매물 등록 및 방문 일정 조율 진행.
2. **무제한 요청 수신 & 최대 3곳 선택 룰**:
   - 다산동 검증 중개사의 매칭 요청은 제한 없이 수신됩니다(중개사는 요청마다 크레딧 1개, 하루 제한 없음 2026-10-29).
   - 집주인은 도착한 요청 중 가장 신뢰할 수 있는 **최대 3곳만 선택하여 중개를 진행**할 수 있습니다. 계약은 그중 1곳과 하며 보수도 그 1곳만 받습니다.
   - (사유: 무분별한 매칭은 매물을 인터넷에 도배시키고 중개사 간 출혈 경쟁을 유발하므로 최대 3곳으로 엄격히 제한).
3. **48시간 자동 종료 & 넛지 룰**:
   - 최대 48시간 동안 지역 중개사에게 매칭 요청이 도달하며, 48시간이 지나면 요청은 자동 종료됩니다.
   - 미성사 시 집주인에게 `"48시간 내 매칭이 성사되지 않을 경우, 복비 조절을 한 번 더 해보세요"`라는 넛지 제공.
4. **협의된 복비 보장**: 매칭이 확정되면 합의한 중개보수로 계약하며, 계약 당일 다시 흥정하지 않습니다(파트너 중개사 법적 서약).
5. **금지 용어 사전**:
   - "계약을 진행할 수 있습니다" ➔ **"중개를 진행할 수 있습니다"**
   - "제한합니다" ➔ **"최대 3곳만 가능합니다"**
   - "선착순 수락" ➔ **"선착순 매칭 요청"**
   - "수수료" ➔ **"중개보수"**

## 2. 통합 관리 센터 (SSOT) 및 데이터/API 위치 총정리

### 2.1 카피라이팅 통합 관리 센터 (`src/config/siteContent.ts`)
대표님이 서비스 내의 모든 문구, 버튼 라벨, 고지 사항, 수치 표기를 개발자 없이 원클릭으로 수정할 수 있는 단일 진실 공급원(SSOT)입니다. 키별 매핑은 [docs/CONTENT_MAP.md](../../docs/CONTENT_MAP.md).

- **관리 영역별 매핑**:
  1. `common`: 브랜드명(`복비`), 지역 배지(`다산동`), 헤더 GNB 라벨(`집주인`, `중개사`)
  2. `home`: 메인 헤드라인, 검색창 플레이스홀더, 3단계 이용 절차, 파트너 중개사 배너, 푸터
  3. `analysis`: 복비 카드(`customizer`: 기본 30% 이유, 4색 구간 문구, 협의 복비 보장), 추천 이유 카드(`recommendationReason`), 맞춤 진단 배너, 매칭 사례(`recentMatches`), 중개사가 받는 금액(`brokerPayout`, Phase 5용), 끝장 투표, 스티키 바
  4. `matchingModal`: 6단계 모달 전체 텍스트 (Step 5 `feeGuaranteeTitle·Desc` 협의된 복비 보장 포함)
  5. `myRequests`: 내 의뢰 내역, 상태 배지, 언마스킹 매칭 확정 뷰
  6. `brokerSignup` · `brokerStrengths`: 중개사 가입(명단 대조·휴대폰·강점 칩·약속·확인 코드)
  7. `legal`: 서비스 이용약관, 개인정보 처리방침, 책임의 한계 (회사 정보는 `COMPANY_INFO` 한 곳)

### 2.2 API 및 데이터 파이프라인 저장 위치
1. **시장 데이터**: `data/market/` → `npm run data:build` → `src/data/market/dasan-market.json` → `src/lib/market/repository.ts`(서버 전용) → 분석 페이지 서버 컴포넌트 `page.tsx` → `AnalysisClient.tsx`
2. **추천 엔진**: `src/lib/analysis/marketEngine.ts` (`recommend`, `feeZone`, `ENGINE_PARAMS`)
3. **법정 중개보수 단일 엔진**: `src/lib/commission.ts` (`calculateLegalCommission`, `computeCommissionQuote`, `commissionFromDiscount`). 화면마다 따로 계산 금지(RULES 규칙 11). `calculateRecommendedCommission`은 레거시(엔진 v3 이전)
4. **AI 설명**: `src/app/api/analysis/explain/route.ts` → `src/lib/analysis/explain.ts` · `gemini.ts`
5. **환경 변수** (이름만, 값은 `.env.local`): 국토부 실거래 키, R-ONE 키, `GEMINI_API_KEY`, Supabase·카카오 (`.env.example` 참고)
6. **클라이언트 브라우저 저장소 (localStorage, 목업 단계)**:
   - `bokbi_active_request_id`, `bokbi_active_owner_phone`, `bokbi_active_request_summary`(의뢰 입력 전체 JSON), `bokbi_debate_votes`
